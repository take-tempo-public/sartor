    ① Produce a bootstrap — runs the live pipeline (paid + slow)
    

      
Runs the full résumé pipeline (analyze → clarify → generate) over the job
        descriptions you paste below, using a real candidate's corpus, then merges the results across
        JDs into one bootstrap.json to annotate.
        Makes paid Sonnet/Haiku calls (~70s per JD) and reuses the same streaming
        engine as the wizard's Analyze.

      
      
No confirmation step. Clicking
        Run bootstrap starts spending straight away — there is no “are you sure?”
        dialog. The number of JD rows you fill in is the only spend control: each row with both a
        name and text is one paid pipeline run.

      
      
How many JDs? Use at least two. The
        point of a bootstrap is comparing the same experience across postings: a bullet that stays
        the same across JDs is the candidate’s real core, while one that changes to echo each
        posting may be stretching to fit it. Each JD usually yields a résumé of about 15–25 bullets
        plus its skills list, and 3–5 clarifying questions to rate. Near-identical bullets and
        skills from different JDs are merged into one item, so each extra JD adds fewer new items
        to label than the one before.

        saved in. Reusing a slug starts a new, separate run in that folder — it does not add
        JDs to an earlier run, and a fixture you have already labeled keeps showing the run you labeled.
        To label several JDs together, put them all in one run.

Give every bullet & skill one verdict before Save (it fail-closes, exactly like
      the CLI): keep — true and usable as written ·
      fix — true but needs rewording (fill in an honest_rewrite) ·
      omit — leave it off the résumé ·
      fabricated — not supported by the candidate's source (add a
      forbidden_pattern regex so the grounding grader flags it next time).
      

    
    
The other fields:
      failed rules — optional tags naming which grading rule an item breaks
      (pick from the suggestions, e.g. invented_metric for a number that
      isn’t in the source); they label the item in the improvement brief, and Save refuses a tag
      that isn’t in the graders’ own list.
      honest rewrite — required for fix: the truthful
      wording you would accept; it becomes a “not OK → OK” example in the improvement brief.
      forbidden pattern — required for fabricated: a
      regular expression describing the invention, so the grounding grader flags it if it shows up
      again in this fixture’s eval runs. Keep it narrow — it should match the invented claim, not the
      candidate’s real work. Examples: managed [0-9]+ engineers
      (an invented team size), saved \$[0-9]+M (an invented dollar
      figure — \$ means a literal $), MIT|Stanford
      (either invented school), \bEpic\b (the word “Epic” on its own).
