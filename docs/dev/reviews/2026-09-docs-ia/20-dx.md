# 20 — Contributor / developer documentation: a DX audit

> **Purpose:** the Epic D / D1 opening audit of Sartor's contributor-facing documentation — how fast a new contributor (human or AI coding agent) reaches a green gate, where the dev onboarding ladder is missing or out-of-order rungs, the signal-to-noise of `docs/dev/`, single-home violations across the contract docs, orphans, and the human-vs-agent split — ranked by severity, with deltas against the 2026-07 UX review.
> **Audience:** `dev` — Epic D D1 input
> **Authoritative for:** the D1 DX findings register (DX-01…DX-19) and the loose-`docs/dev/*.md` classification table below, as observed at `88c0011` on `feat/docs-ia-design` (2026-09-27). Not authoritative for any rule it quotes — those stay in their homes.

**Method.** Read-only walk of the path a newcomer takes: `README.md` → `CONTRIBUTING.md` → `AGENTS.md` / `CLAUDE.md` → `docs/architecture.md` → `docs/system-model.md` → `docs/PRODUCT_SHAPE.md` → `docs/dev/` → `docs/governance/` → `docs/wiki/` → `docs-site/content/docs/dev-*.mdx`. Every finding carries a `path:line` or a quoted command with its count. Inbound-reference counts are **basename greps over tracked files, excluding `docs/dev/handoffs/` and `docs/dev/ledger/`** (so a hit from a handoff doesn't count as navigation) — a basename grep can miss a link written without the `.md` suffix, so "zero inbound" is an upper bound on orphans, not proof. Nothing was run except `git`/`grep`/read-only Python; the gate and the app were not run.

**Baseline.** Findings already in [`../2026-07-ux-review/30-technical-user.md`](../2026-07-ux-review/30-technical-user.md) and [`../2026-07-ux-review/50-oss-polish-plan.md`](../2026-07-ux-review/50-oss-polish-plan.md) are not re-reported as new; their current status is in [§ Deltas vs the 2026-07 baseline](#deltas-vs-the-2026-07-baseline).

## Findings (ranked)

### HIGH

**DX-01 — Four live, disagreeing definitions of "the gate."** `scripts/gate.py` says it is *the* single definition (`scripts/gate.py:1-7`), and its `_STEPS` run **six** steps: `ruff check`, `ruff format --check`, `mypy`, `pytest -m "not ux" -n auto`, `pytest -m ux`, `work_items check` (`scripts/gate.py:72-82`). The docs that describe it disagree with it and with each other:
- `AGENTS.md:229` and `AGENTS.md:280`, `CONTRIBUTING.md:34-35`, `CONTRIBUTING.md:86`, `docs/architecture.md:905-906` all describe **four** steps (no pytest split, no `work_items check`).
- `README.md:274` still shows the pre-gate bar `ruff check . && mypy . && pytest  # the minimum bar; CI runs the same` — no `ruff format`, no `work_items`, and not `python -m scripts.gate` at all, even though it labels CONTRIBUTING as canonical on the line above (`README.md:272`).
- `docs/install.md:668-697` ("Verifying the install") offers a third bar: `python -m pytest -q` ("Should report `1200+ passed`") plus `ruff check .`.
The restatements are exactly the drift gate.py was built to end ("defined independently in three places … with no mechanism to keep the three in sync", `scripts/gate.py:3-5`). *Delta:* new since baseline (gate.py is PX-55, post-2026-07 review).

**DX-02 — Time-to-first-green-gate is findable but not budgetable.** The command is fast to find for a human (`CONTRIBUTING.md:36`, 36 lines in, linked from `README.md:59`). What a newcomer is not told before they run it: the real runtime (~30 min full suite; non-UX ~437 s under `-n auto`, `scripts/gate.py:25-29`), that the UX tier is serial by design (`scripts/gate.py:31-37`), and that a memory preflight refuses to start below 1.0 GB free (`scripts/gate.py:39-44`, `_MEMORY_FLOOR_GB = 1.0`). `grep -n "30 ?min\|~30\|minutes" CONTRIBUTING.md AGENTS.md` returns 0 hits. The only runtime pointer is buried at the end of a 1-line checklist item (`CONTRIBUTING.md:86` → `docs/dev/perf/TEST_SUITE_PERFORMANCE.md`). For an agent, `python -m scripts.gate` first appears at `AGENTS.md:158` inside the C-11 section and gets its own section only at `AGENTS.md:271` (88% of the way down a 308-line file). A contributor who hits the refusal or a 30-minute wait with no warning reads it as a failure.

**DX-03 — Contradictory merge instructions, one of them inside a recommended subagent.** `AGENTS.md:232` is binding: "a local `git merge` to `main` is NEVER the flow" (PR + `gh pr merge --merge`; squash/rebase disabled). But `CONTRIBUTING.md:58` tells humans "Merge with `git merge --no-ff`", and the `git-flow` subagent — which `CLAUDE.md:162-166` tells agents to "prefer delegating to" — says it "Honors CLAUDE.md rules (… --no-ff merges …)" (`agents/git-flow.md:3`) and "Merge feature branches with `git merge --no-ff`" (`agents/git-flow.md:19`). `CLAUDE.md` contains no `--no-ff` rule (`grep -c "no-ff" CLAUDE.md` = 0), so the agent cites a home that doesn't hold the rule it claims.

**DX-04 — The "universal contract" is written for the owner's session, and CONTRIBUTING sends outside humans into it.** `CONTRIBUTING.md:11-12` and `CONTRIBUTING.md:44` say AGENTS.md's rules "apply to humans" too. The close-out checklist `AGENTS.md:210-233` then requires things only the owner's machine or session can do: a provenance-ledger file `docs/dev/ledger/<session>.jsonl`, the `~/.claude/plans/.approved` marker, a stamped handoff at `docs/dev/handoffs/<branch-slug>.md` validated by `scripts/verify_doc_template.py`, a scoped `/wiki-self-update` (a Claude Code plugin command), and filing into the Carry-forward ledger inside the 4,424-line `RELEASE_CHECKLIST.md` (ledger at `docs/dev/RELEASE_CHECKLIST.md:505`). There is no "external contributor / fork PR" lane that says which of these apply to them. The contract doesn't separate **rules about the code** (security gate, deterministic boundary, `PROMPT_VERSION`, no-invention) from **the owner's session protocol** (handoffs, ledger, plan markers, pointer checks) — and that split is the one D1 needs.

**DX-05 — Publication to the docs site is decided by an accident of formatting, and two scripts define "published" differently.** `scripts/project_docs_to_mdx.py:607-622` publishes **any** tracked `.md` (outside `docs/wiki/`) whose opening blockquote carries all three P/A/A labels. A Python scan of `docs/dev/**` finds **25** files with the full triad in their first 3,000 chars (an estimate — the projector's contiguous-blockquote parse may drop some), and they include process records nobody curated for publication: `docs/dev/diagnosis/compose-summary-draft-settle-hole.md`, `docs/dev/handoffs/epic-b-design-brief.md`, `docs/dev/handoffs/epic-c-design-brief.md`, `docs/dev/handoffs/EPIC_SPRINT_BRIEF_TEMPLATE.md`, `docs/dev/reviews/epic-c-console-ux-audit.md`, `docs/dev/V1_0_5_VERIFICATION.md`. Meanwhile live references without the triad are **not** published: `AGENT_HANDOFF_TEMPLATE.md`, `AGENT_FAILURE_PATTERNS.md`, `RELEASE_ARC.md`, `GROUNDING_METRIC.md`, `decisions.md`. Separately, the frontmatter gate `scripts/check_doc_frontmatter.py:44-69` uses a hand-kept 16-file registry (root + `docs/*.md` + governance) and says it "should converge with [the projector's] scope rather than duplicate it as a second definition" (`scripts/check_doc_frontmatter.py:24-27`) — it hasn't. The rendered nav `docs-site/content/docs/meta.json` is one flat list of 37 slugs: user pages, then `agents`/`claude`/`contributing`, then 20 `dev-*` pages in arbitrary order (the local build is gitignored, `.gitignore:134`, and may lag HEAD — it shows 20 `dev-*` pages vs the ~25 eligible at HEAD).

The L0→L3 one-way chain and the D5 carve-out for `AGENTS.md`/`CLAUDE.md` (`:141-144`) still hold and are worth keeping.

## What an AI agent needs vs what a human contributor needs

| Need | AI coding agent | Human contributor |
|---|---|---|
| Entry | auto-loaded `AGENTS.md` + `CLAUDE.md` (~42 KB, every session) — so **every byte is a recurring cost**, and rules must be inline because a non-Claude agent can't follow `@imports` (`AGENTS.md:24-30`) | `README.md` → `CONTRIBUTING.md`; will not read 308 lines of contract before a first PR |
| First command | the gate and its runtime/memory budget stated early, so a long run isn't misread as a kill (DX-02; the 0001 and 0108 work items record exactly that misreading, `scripts/gate.py:22-27`, `:39-44`) | the same, plus `SARTOR_DEMO=1` to see the app without a key (DX-13) |
| Rules | hook semantics, the "no escape hatch" rules, evidence/consumer dossiers — machine-checked, needed at the moment of the edit | the *code* rules (security gate, deterministic boundary, `PROMPT_VERSION`, no-invention) — not the owner's session protocol (DX-04) |
| Navigation | exact paths and one canonical home per fact; a stale catalog (DX-09) misroutes delegation directly | a task-shaped "where do I change X" index (DX-13) |
| Records | handoffs, ledger, diagnosis dossiers are **inputs** (pointer check, `restore-evidence`) | noise, unless debugging the history of a specific item |

## Implications for the D1 IA design

1. **Split `docs/dev/` by document *kind* before by topic:** `reference/` (live, P/A/A-headed, publishable), `records/` (handoffs, ledger, diagnosis, blast-radius, reviews, perf runs — append-only, never published), `templates/` (the five templates, DX-08), with `work/` staying generated. Use the loose-file table above as the starting assignment.
2. **Make publication an explicit opt-in, not header presence.** One registry (or an `audience`+`publish` frontmatter key) consumed by *both* `project_docs_to_mdx.py` and `check_doc_frontmatter.py`, so "published" has one definition (DX-05).
3. **Give the site nav real sections** — `user` ladder, then `dev` ladder — generated from that registry's order, not a flat `meta.json` (DX-05, DX-06).
4. **Start the dev ladder where the user ladder ends:** demo mode → install `[dev]` → `python -m scripts.gate` (with runtime + memory budget) → first change (task index) → the code rules → governance depth (DX-02, DX-13).
5. **Every gate description should cite `scripts/gate.py`, not restate its step list.** Better: have the gate print its own step list, and add a doc test that fails if any doc enumerates steps that don't match `_STEPS` (DX-01; C-11 says a mechanism, not a note).
6. **Split AGENTS.md into "rules about the code" (universal, for humans and any agent) and "the owner's session protocol"** (handoffs, ledger, plan markers, pointer checks — an owner-lane doc AGENTS.md links to). Keep the inline carve-out only for the first half; this also cuts the ~42 KB always-loaded budget (DX-04).
7. **One home each for the plugin catalog and the hook catalog,** generated from `agents/`, `commands/`, `skills/` and `.claude/settings.json` (or checked against them by a test); README/CONTRIBUTING link instead of listing (DX-09, DX-10).
8. **Add `docs/dev/README.md` as the dev front door** — a short routed index (reference · runbooks · designs · records · templates), not an encyclopedia (DX-07).
9. **Revise `documentation-architecture.md` in the same D1 branch** that changes the layout: correct the four drifted claims, and model `docs/dev/` as several layers, not one L1 blob (DX-06).
10. **Archive the six stale loose docs and move the 12 process records out of the loose root**; move the historical sections of `PRODUCT_SHAPE.md` / `RELEASE_CHECKLIST.md` into records, and give the Carry-forward ledger a home of its own (DX-07, DX-15).
11. **Re-section `docs/wiki/index.md` by audience and task** instead of ingest batch, so the `user`/`dev` plane structures the wiki, the site and the avatar alike (DX-14).
12. **Fix the three contradictions as D1 prerequisites, not IA work:** the `--no-ff` merge rule (`CONTRIBUTING.md:58`, `agents/git-flow.md:3,19`), the "latent CI" claim (`CONTRIBUTING.md:114`, `ci.yml:64-67`), and the pre-blueprint import rule (`docs/architecture.md:311`) — each would otherwise be carried into the new layout (DX-03, DX-11, DX-12).
